## 一、为什么要做这个栏目

当前站点内容只有一种形态：技术实操（已发布 1 篇 SSH 加固实录）。

| 问题 | 表现 |
| --- | --- |
| 受众窄 | 只有运维/开发会搜「ssh 加固」，创业者、产品经理不会来 |
| 无差异 | 技术教程全网都有，缺少「别处没有的判断」 |

手上已经有的、别人抄不走的是：**为了给自己的产品选技术，实际部署并测过一批开源项目，并且测出了失败。**

那批失败（深爬静默降级、缓存返回空内容、LLM 静默改数据）正是商业判断的依据——只有真跑过的人才写得出「这个能力现在不能对外承诺」。

所以栏目的核心不是「介绍开源项目」，而是：

> **用实测证据回答「这个项目能不能变成生意」。**

### 目标

| # | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 建立可被搜索引擎收录的独立栏目 | `/open-source` 及其下页面进入 sitemap 且被收录 |

| 不做 | 原因 |

| 新建一套内容系统 | blog + topic + category + tag 已够用 |

## 三、信息架构

```
栏目（category）        开源项目商业观察
                          │
项目档案（oss_project）  Crawl4AI        ← 一个项目一条
                          │
文章（blog）             商业分析 / 技术研究 / 实践
                          │
专题（topic）            Crawl4AI 深度研究（可选，用于连载）
```

| 层 | 承载 | 回答什么 |
| --- | --- | --- |
| 文章栏目 | `category` | 这篇属于哪个内容中心 |
| 项目领域 | `oss_project.category`（枚举） | 这个项目属于哪个技术领域 |
| 技术主题 | `tag` + `blog_tag` / `oss_project_tag` | 讲的是哪项技术 |
| 连载 | `topic` + `topic_article` | 系列里的第几篇 |

**两套分类不要混**：文章栏目是「内容中心」（开源项目商业观察），项目领域是「技术领域」（数据采集与搜索）。前者动态可加，后者固定 6 个。

### 与作品集的边界

| | `/projects`（作品集） | `/open-source`（本栏目） |
| --- | --- | --- |
| 内容 | 我自己的作品 | 第三方开源项目 |
| 目的 | 展示能力 | 分析商业价值 |
| 表 | `portfolio` | `oss_project` |
| 状态 | `enabled` 开关 | `publish_status` + `research_status` 双状态机 |

两套完全独立，互不影响。

### 4.0 一条硬规则：文章只有一个 URL

技术研究与商业分析文章，**URL 一律是 `/blog/{slug}`**，不再生成 `/open-source/{slug}`。

理由：同一内容两个地址，搜索引擎判重复，权重被稀释；而且要维护两套 canonical。

关键词已经由 slug 本身承载：

```
/blog/crawl4ai-business-analysis      ← 商业分析
/blog/crawl4ai-architecture           ← 技术研究
```

栏目页只做**聚合**（列表、分类、标签、项目档案），不复制文章正文。

> 这条与规划文档里 `/open-source/crawl4ai-business-analysis` 的设计不同，属于有意偏离。

### 4.1 已确认：导航入口

`nav_menu` 现有 6 个可见项（V26 `nav_final_six`）：首页 / 技术文章 / 技术专题 / 项目 / 知识产品 / 技术服务。

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A 加第 7 项**（已确认） | 插入 `/open-source`，**sort=25**（技术文章 20 与 技术专题 30 之间） | 栏目有一级入口；不改变其余各项相对顺序 | 导航由 6 项变 7 项 |
| B 复用「项目」格 | `/projects` 页内两个 tab | 导航不变 | 两类内容语义不同；要改现有页面 |
| C 挂在「技术专题」下 | `/topic` 页顶部加入口 | 不动导航 | 曝光最低 |

**已确认采用 A**（2026-11-20 视觉评审）。位置定在「技术文章」之后，因为它属于内容栏目，
跟技术专题/项目同组；早前建议的 45（项目之后）已废弃。

## 六、SEO

现状：Nuxt 3 SSR 已开，`sitemap.xml.ts` 手写，`robots.txt.ts` 已存在。

### 6.1 必做

| # | 项 | 做法 |
| --- | --- | --- |
| S1 | sitemap | 加 `/open-source`、`/open-source/category/*`、所有 `published` 项目页 |
| S2 | 元信息 | 项目页 `name + 一句话定位`；列表页 `栏目 + 领域` |
| S3 | canonical | 全部指向自身；**文章页不设指向栏目页的 canonical**（因为栏目不复制正文） |
| S4 | 结构化数据 | 项目页 `TechArticle` + `BreadcrumbList`；文章页补 `BreadcrumbList` |
| S5 | 内链 | 档案 ↔ 文章双向；同标签项目互链 |
| S6 | 草稿隔离 | `draft` / `archived` 项目不进 sitemap、页面 404 |

### 6.2 不做

- 不做 `Review` / `AggregateRating`（无真实用户评分，滥用会被判垃圾结构化数据）
- 不在标题堆关键词

### 6.3 可预期的搜索入口

```
「Crawl4AI 商业价值」      → 项目档案
「Crawl4AI 能不能商用」    → 商业分析文章
「crawl4ai 部署」          → 技术实践文章
「开源项目 商业模式」      → 栏目首页
```

长尾在「某项目 + 能不能/值不值」这类问句上。

## 七、内容要求

| 类型 | 模板 | 位置 |
| --- | --- | --- |
| 技术研究 | `ARTICLE-STANDARD.md` 十节 | 研究仓 `docs/publishing/` |
| 商业观察 | `COMMERCIAL-REVIEW-STANDARD.md` 十维 + 评估卡 | 同上 |

硬规则：

1. 没有实测的项目，评估卡全部标「待验证」，不得凭 README 编写
2. star 数只作关注度参考，**不作为任何档位的判定依据**
3. 结论档必须是五档之一
4. 每格评估结论标证据等级 `F/S/T/M/A/?`
5. `last_verified_at` 必须填写，且不能早于资料引用日期

## 八、验收标准

- [ ] `/open-source` 匿名可访问，SSR 输出含项目名（`curl` 直接可见）
- [ ] 至少 1 个 `published` 项目档案，评估卡七项完整渲染
- [ ] `draft` 项目：列表不出现、详情 404、sitemap 不含
- [ ] 档案页可跳转关联文章，文章页可跳回档案
- [ ] 文章 URL 只有 `/blog/{slug}` 一种，无重复内容
- [ ] sitemap 含栏目与项目页且返回 200
- [ ] 后台可新建/编辑、设置双状态、维护关联与标签
- [ ] 移动端 375px 不溢出
- [ ] 空数据状态不显示 `undefined`

## 九、风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 首批选题无证据 | 写了 9 篇里 6 篇是搬运，可信度一次性毁掉 | 首批只发有实测的项目 |
| 评估卡变打分游戏 | 读者只看档位不看条件 | 不设总分，只给五档 + 每格条件 |
| 商业判断被当承诺 | 「值得部署使用」被理解成「保证能跑」 | 档案页固定声明：结论基于特定版本与环境 |
| 两张项目表混淆 | 新人把 `portfolio` 和 `oss_project` 搞混 | 命名与注释；ADR-0004 记录理由 |
| 空栏目曝光浪费 | 建了 3 个栏目只有 1 个有文章 | 只建实际会用的 3 个，其余 V29 再加 |
