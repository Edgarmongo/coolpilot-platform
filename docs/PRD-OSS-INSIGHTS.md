# PRD：开源项目商业观察

> 栏目名：**开源项目商业观察**（Open Source Business Insights）
> 版本：v1.0 · 2026-11-20
> 状态：待评审

---

## 一、为什么要做这个栏目

当前站点内容只有一种形态：技术实操（已发布 1 篇 SSH 加固实录）。

这带来两个问题：

| 问题 | 表现 |
| --- | --- |
| 受众窄 | 只有运维/开发会搜「ssh 加固」，创业者、产品经理不会来 |
| 无差异 | 技术教程全网都有，缺少「别处没有的判断」 |

而手上已经有的、别人抄不走的东西是：**为了给自己的产品选技术，实际部署并测过一批开源项目，并且测出了失败。**

那批失败（深爬静默降级、缓存返回空内容、LLM 静默改数据）正是商业判断的依据——**只有真跑过的人才写得出「这个能力现在不能对外承诺」。**

所以栏目的核心不是「介绍开源项目」，而是：

> **用实测证据回答「这个项目能不能变成生意」。**

## 二、目标与非目标

### 目标

| # | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 建立可被搜索引擎收录的独立栏目 | `/open-source` 及其下页面进入 sitemap 且被收录 |
| G2 | 首批形成可读的内容密度 | 6 个月内 12 篇（其中项目档案 ≥ 4 个） |
| G3 | 每篇商业分析都能追到实测证据 | 100% 文章有评估卡且每格标证据等级 |
| G4 | 与技术研究栏目形成互链 | 每篇商业分析至少链 2 篇技术文章 |

### 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| 新建一套内容系统 | 现有 blog + topic + portfolio 已能承载，见 `DATA-MODEL-OSS.md` |
| 做「开源项目导航站」 | 那是目录型产品，靠收录量取胜，与「有判断」冲突 |
| 自动抓 GitHub 生成文章 | 会退化成 README 翻译，直接毁掉栏目可信度 |
| 给项目打总分排名 | 一个数字无法承载「什么条件下值得做什么」，见评估卡设计 |
| 第一期就拆 `oss_project` 独立表 | 字段与 `portfolio` 重合 90%，先复用 |

## 三、信息架构

三层，各自职责不同：

```
栏目（category）        开源项目商业观察
                          │
专题（topic）            Crawl4AI 深度研究
                          │
项目档案（portfolio）    Crawl4AI  ← 一个项目一条档案
                          │
文章（blog）             商业价值分析 / 架构解析 / 部署实战 ...
```

| 层 | 承载表 | 回答什么 | 数量级 |
| --- | --- | --- | --- |
| 栏目 | `category` | 这篇属于哪个内容中心 | 4–5 个 |
| 专题 | `topic` | 这个系列读到哪了 | 每项目 1 个 |
| 项目档案 | `portfolio` | 这个项目是什么、值不值得 | 每个被分析项目 1 条 |
| 文章 | `blog` | 具体分析/教程 | 不限 |

**为什么不把项目信息写进每篇文章**：同一个项目会有 4–6 篇文章（商业分析、架构、部署、集成），项目基本信息（GitHub、License、技术栈、结论档位）应该只有一份。

### 四个内容中心

| 栏目 | 定位 | 主要受众 |
| --- | --- | --- |
| 开源项目商业观察 | 这项目能不能赚钱 | 创业者、独立开发者、企业技术负责人 |
| 开源技术研究 | 它怎么工作的 | 开发者 |
| AI 应用实践 | 怎么把它跑起来 | 开发者、实施工程师 |
| 商业实践与案例 | 真实项目里的成本与效果 | 企业客户、同行 |

> **category 的语义升级**：现有三个分类（文章 / 知识库 / AI工具集）是「形态」维度，但所有文章都在「文章」里，等于没分类。
> 本期把 category 改为**栏目**维度。详见 `DATA-MODEL-OSS.md` §5 的迁移方案。

## 五、交互细节

| 场景 | 行为 |
| --- | --- |
| 栏目首页筛选 | 前端按 `tag` 过滤已加载列表，不重新请求（列表量小） |
| 档案详情无正文 | 只显示评估卡 + 文章列表，不显示空正文区 |
| 评估项未评 | 显示「待验证」灰标，不显示空值或 0 |
| 结论档位为空 | 不显示标签，不默认成任何档 |
| 文章列表为空 | 显示「分析正在整理中」，链接到专题页 |

## 六、SEO 方案

现状：Nuxt 3 SSR 已开，`server/routes/sitemap.xml.ts` 手写，`robots.txt.ts` 已存在。

### 6.1 必做

| # | 项 | 具体做法 |
| --- | --- | --- |
| S1 | sitemap 收录新页面 | 在 `staticPaths` 加 `/open-source`；遍历 `portfolios` 输出 `/open-source/{slug}`（仅 `kind=oss` 且 `enabled`） |
| S2 | 页面 title/description | `useHead` 按栏目与档案分别设置，archive 用 `name + 一句话定位` |
| S3 | canonical | 每页 `<link rel="canonical">` 指向 `siteUrl` 绝对地址 |
| S4 | 结构化数据 | 档案页 `TechArticle` + `BreadcrumbList`；文章页补 `BreadcrumbList` |
| S5 | 内链 | 档案 ↔ 文章双向；同 tag 项目互链 |
| S6 | 分页 | 列表分页加 `rel="prev"/"next"`（当前文章列表已有分页则沿用） |

### 6.2 不做

- 不做 `Review` / `AggregateRating` schema —— 我们没有用户评分，滥用会被判垃圾结构化数据
- 不做栏目页的关键词堆砌 —— 标题就是「开源项目商业观察」，不写「开源项目商业观察_开源项目分析_开源项目推荐」

### 6.3 可预期的收录路径

```
「Crawl4AI 商业价值」      → 档案页
「Crawl4AI 能不能商用」    → 商业分析文章
「crawl4ai 部署」          → 技术文章
「开源项目 商业模式 分析」  → 栏目首页
```

长尾在「某项目 + 能不能/值不值」这类问句上，这是栏目最容易吃到流量的地方。

## 七、内容要求

### 7.1 两类文章，两套模板

| 类型 | 模板 | 位置 |
| --- | --- | --- |
| 技术研究 | `ARTICLE-STANDARD.md` 十节 | 研究仓 `docs/publishing/` |
| 商业观察 | `COMMERCIAL-REVIEW-STANDARD.md` 十维 + 评估卡 | 同上 |

### 7.2 硬规则

1. **没有实测的项目，评估卡全部标「待验证」**，不得凭 README 编写
2. star 数只能作为「关注度」参考，**不得当作市场需求的证据**
3. 结论档位必须是五档之一，不得自定义（否则无法筛选）
4. 每格评估结论标证据等级 `[V]/[S]/[D]/[?]`

## 八、验收标准

栏目可上线，当且仅当：

- [ ] `/open-source` 匿名可访问，SSR 输出含档案与文章标题（非纯客户端渲染）
- [ ] 至少 1 个 `kind=oss` 的项目档案，评估卡完整渲染
- [ ] 档案页可跳转到关联文章，文章页可跳回档案
- [ ] sitemap 含 `/open-source` 与档案 URL，且返回 200
- [ ] 后台可新建/编辑档案，可设置 kind、评估卡、结论档位
- [ ] 移动端 375px 宽度下卡片不溢出
- [ ] 空数据状态下页面不报错、不显示 `undefined`

## 九、风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **首批选题无证据** | 写了 9 篇里 6 篇是搬运，栏目可信度一次性毁掉 | 首批只发有实测的 2 个项目；其余标「研究中」 |
| 评估卡变成打分游戏 | 读者只看总分不看条件 | 不设总分，只给五档结论 + 每格条件 |
| 商业判断被当成承诺 | 「值得部署使用」被理解为「保证能跑」 | 档案页固定声明：结论基于特定版本与环境，不构成交付承诺 |
| portfolio 与 projects 语义混 | 自己的作品和被分析项目混在一个列表 | `kind` 字段强隔离，`/projects` 只显示 `own` |
