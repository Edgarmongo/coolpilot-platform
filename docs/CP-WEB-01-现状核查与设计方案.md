## 0 先看结论

### 0.1 任务卡里有四条假设与项目实际不符，必须先对齐

| # | 任务卡假设 | 项目实际 | 影响 |
|---|---|---|---|
| 1 | 前台用 **Next.js + React** | 已经是 **Nuxt 3 + Vue 3**（SSR 正常，`sitemap.xml`/`robots.txt` 已实现） | 不需要迁移。硬迁 Next.js 等于重写整个前台，收益为零 |
| 2 | 需要新建「技术服务」体系 | 已是 **product(type=SERVICE) + service_item 扩展表**，且已有需求→报价→立项→里程碑→交付→验收整条链路 | 不要重复建表，只补展示层 |
| 3 | 需要新建 `social_account` 表管社交账号 | `site_setting` type=2 **已有存量**（GitHub / Telegram / QQ / bilibili / 网易云 / email） | 不能另起一套，否则两处配置打架 |
| 4 | 建 5 张表做渠道与转化统计 | 个人站日 PV 量级很小，`visit_log` 已在记录每次访问 | 5 张表偏重，建议 1 张表 + 1 组 KV + 3 个字段 |

### 0.2 可复用程度

**约 75% 可复用，不推翻现有架构。** 真正要新建的只有两块：`/follow` 关注我页、`/planet` 知识星球页，以及后台对应的两个配置页。

### 0.3 一句话判断

任务卡的方向（内容获客 → 三条转化路径）是对的，但它把「新建一套系统」当成了前提。实际情况是：**内容中心、知识产品、技术服务、订单交易全都已经能跑，缺的是「首页叙事」和「两个外链落地页」。**

### 1.5 站点设置的存储方式（关键约束）

`site_setting` 的字段是 `id / type / name_zh / name_en / value / value_en`。

**注意：没有稳定的 `key` 字段，配置项是靠「中文名」识别的。**

| type | 分组 | 现存项 |
|---|---|---|
| 1 | 站点基础 | 站点名称、标题后缀、页脚文案、ICP、赞赏码、播放器、品牌标记等 15 项 |
| 2 | **个人资料 / 社交账号** | 头像、昵称、滚动个签、**GitHub、Telegram、QQ、bilibili、网易云、email**、自定义 ×3 |
| 3 | 徽标 | 7 个徽标（JSON） |
| 4 | 友链页 | 页面说明、评论开关 |
| 5 | 收款 | 微信码、支付宝码、PayPal 链接、收款人 |

**这里有两个事实必须写进设计约束：**

1. **type=2 已经是社交账号配置了**，但它只有「一行一个链接」，没有二维码、没有平台枚举、没有排序、没有启用开关。
2. **前台完全没有消费 type=2**（全量 grep 无引用）。也就是说这 6 个社交账号配置在库里躺着，前台一个都没展示——这正是任务卡想解决的「关注我」，但已有半成品数据。

> 设计含义：`social_account` 不是从零新建，而是**把 type=2 的存量升级成结构化表**，旧值需要迁移，否则站长会发现「我明明配过 GitHub，怎么新页面是空的」。

### 1.6 文件 / 图片 / 二维码存储

| 能力 | 接口 | 说明 |
|---|---|---|
| 后台上传 | `POST /admin/file/upload` | 参数 `bizType`（默认 PRODUCT）+ `isPublic`，可传任意业务类型 |
| 前台用户上传 | `POST /file/upload` | 仅允许 `PROOF` / `AVATAR` / `OTHER` |
| 取临时访问 | `GET /file/token` | 私有文件用 |
| 下载 | `GET /file/download` | — |

- 落盘位置：容器内 `/data/upload/`，Docker 卷持久化。
- `bizType` 是自由字符串，**新增 `SOCIAL_QR`、`PLANET_COVER` 不需要改后端**。
- 站点设置里的图片字段已支持「缩略图 + 地址 + 上传」三件套（之前那一批做过）。

**结论：二维码和星球封面直接复用现有上传，不需要新的存储能力。**

### 1.7 访问统计与来源能力

**已有**

- `visit_log`：uuid、uri、method、param、behavior、content、ip、ip_source（省|市）、os、browser、耗时、UA、时间。共 653 条。
- `visitor`：访客标识（uuid）去重。
- `visit_record`：每日 PV/UV。`city_visitor`：城市维度新增访客。
- Redis 实时浏览量 + 每日 0 点/1 点两个定时任务落库。
- 后台仪表盘：今日访问量。

**缺口（这是本次最实质的技术缺口）**

`visit_log` **没有 referer / utm_source / landing_page 字段**。因此：

- 无法回答「这个访问是从抖音还是小红书来的」
- 无法回答「哪个渠道带来的咨询最多」
- 任务卡第六节要的「渠道效果分析报表」，**以现在的表结构做不出来**

另外 `visit_log` 记录的是**后端接口调用**（AOP 切面），不是前端页面浏览。同一次页面访问会产生多条接口记录（实测一次首页加载产生 3 条 `/blogs` 记录），所以**不能直接把 `visit_log` 行数当 PV**。

| 项 | 状态 | 说明 |
|---|---|---|
| SSR 渲染 | ✅ | Nuxt 3，文章正文在 HTML 里 |
| `sitemap.xml` | ✅ | 手写 server route，静态页 + 文章动态生成 |
| `robots.txt` | ✅ | 手写 server route |
| 每页 `title` | ✅ | 页面级 `useHead` |

## 2 四处冲突的处理建议

### 2.1 技术栈：坚持 Nuxt 3，不迁 Next.js

任务卡写 Next.js，但项目已是 Nuxt 3 且双语、SEO 基础、AI 问答、收银台全都在上面跑。

- 迁移成本：整个前台重写，约等于把过去所有批次作废。
- 迁移收益：**零**。两者都是 SSR 框架，对 SEO 的能力没有实质差别。
- 建议：以 Nuxt 3 为准，任务卡里「Next.js + TypeScript + React」这一行改为「Nuxt 3 + Vue 3」。

### 2.2 技术服务：只补展示，不建新体系

技术服务不是「待建」，而是**已经完整**：

```
product(product_type=SERVICE, deal_mode=DIRECT/QUOTE/BOTH)
  └─ service_item（服务范围、交付周期、流程、FAQ）
demand → quote → project → milestone → delivery → 验收
```

前台 `/service` 已在跑（2 个服务），后台「技术服务」菜单已有 6 个子页。

**建议：仅在服务详情页补「案例」「合作流程」两个展示区块，不新增表。**

### 2.3 社交账号：升级存量，不另起炉灶

`site_setting` type=2 已经有 6 个账号。若新建 `social_account` 而不迁移，会出现「后台两处都能配社交账号」的混乱。

**建议：建 `social_account` 表，同时写迁移把 type=2 的 6 条旧数据搬进去，然后把 type=2 里这几项标记为废弃（保留行，不删，避免历史脚本 checksum 问题）。**

### 2.4 统计：1 张表 + 3 个字段，不建 5 张表

任务卡建议 5 张表。逐条评估：

| 任务卡的表 | 建议 | 理由 |
|---|---|---|
| `social_account` | ✅ **建** | 需要平台枚举、二维码、排序、启停，KV 撑不住 |
| `promotion_config`（知识星球） | ❌ 不建表，用 `site_setting` type=6 | 只有 1 条记录、5 个字段，建表是过度设计 |
| `promotion_channel` | ❌ 不建表 | 渠道就是固定几个（douyin/xiaohongshu/zhihu/wechat/github），UTM 参数本身就是渠道编码，不需要一张表来存「渠道字典」 |
| `traffic_event` | ❌ 不建表，给 `visit_log` 加 3 列 | 已有 653 条访问日志，加 `utm_source / referer / landing_page` 即可，比新建事件表省一个双写链路 |
| `conversion_event` | ⚠️ **用轻量方案** | 见下 |

**转化事件的做法**：不建全量事件表，只在两个「真正要看的动作」上加计数——

1. 知识星球按钮点击
2. 技术服务咨询提交（这个已经落在 `demand` 表，天然可统计）

前者用「前端上报 → 落 `visit_log`（behavior='外链点击'，content=星球/平台名）」即可，不需要新表。

> 判断依据：个人站日 PV 量级在几十到几百，用事件表做全量埋点是给未来十万级流量准备的架构，现在做只会增加维护成本。**等真有量了再拆表，那时数据迁移也是小的。**

## 5 数据模型建议

### 5.1 新增 1 张表：`social_account`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint PK | |
| `platform` | varchar(32) | 枚举：WECHAT / DOUYIN / XIAOHONGSHU / ZHIHU / GITHUB / BILIBILI / TELEGRAM / QQ / EMAIL / CUSTOM |
| `account_name` | varchar(64) | 显示用账号名 |
| `intro` | varchar(255) | 一句简介 |
| `home_url` | varchar(512) | 主页链接，可空（纯二维码平台可不填） |
| `qr_file_id` | bigint | 二维码文件，关联 `file.id`，可空 |
| `icon` | varchar(32) | 图标标识（前端内置图标集，避免引入图标库） |
| `sort` | int | 升序，10/20/30 |
| `enabled` | bit(1) | 是否展示 |
| `create_time` / `update_time` | datetime | |

**为什么存 `qr_file_id` 而不是 URL**：现有 `file` 表已经是文件元信息的唯一来源，存 id 能复用「私有文件换 token」「删除时能查引用」这些已有能力；直接存 URL 会在文件被清理后变成裂图。

### 5.2 新增 1 组 KV：`site_setting` type=6（知识星球）

| name_zh | 说明 |
|---|---|
| 知识星球名称 | 显示名 |
| 知识星球封面 | 图片路径 |
| 知识星球介绍 | 富文本/多行 |
| 知识星球链接 | 官方跳转地址 |
| 知识星球二维码 | 图片路径 |
| 知识星球启用 | 0/1，关闭则首页卡片与 `/planet` 都不显示 |

> 复用现有 `site_setting` 机制的好处：后台「站点设置」页已经能按 type 动态生成 tab（上一批做过），加 type=6 只需插数据，**前端 tab 会自动出现**。

### 5.3 改 1 张表：`visit_log` 加 3 列

| 字段 | 类型 | 说明 |
|---|---|---|
| `referer` | varchar(512) | 来源页 |
| `utm_source` | varchar(64) | douyin / xiaohongshu / zhihu / wechat / github |
| `landing_page` | varchar(255) | 落地页路径 |

采集方式：前台 `app.vue` 或中间件读 `route.query.utm_source` + `document.referrer`，首次进入时写入 cookie/localStorage，后续接口请求带上；后端 `VisitLogger` 切面透传落库。

**这是「渠道效果分析」的唯一硬前提。** 没有这 3 个字段，任务卡第六节的报表做不出来。

### 5.4 不建的表及理由

见 §2.4。总结：`promotion_channel` / `promotion_config` / `traffic_event` / `conversion_event` 四张表在当前数据量级下都是过度设计，用 KV + 现有日志表扩展即可，等量级上来再拆。
