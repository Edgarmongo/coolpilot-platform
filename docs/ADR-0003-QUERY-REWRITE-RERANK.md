# ADR-0003：追问改写与重排

- 状态：已采纳
- 日期：2026-11-06
- 相关：ADR-0001（向量存储）、ADR-0002（混合检索）

## 背景

ADR-0002 之后，检索的「找得到」问题基本解决了（同义改写、跨说法召回都正常），
但还剩两个缺口，都在**问题本身**和**排序**上，而不是召回：

1. **追问缺上下文**。「那退款呢」「它的评估指标有哪些」这类句子，
   代词与省略成分指向上一轮。字面检索看不到这层关系，向量也测不准 ——
   一整个句子只有几个字是实词，剩下的全是指代。
   改造前的兜底是「本轮 + 上一轮」硬拼成一句去检索，拼出来的句子语义模糊，
   等于把判断权交给了打分函数。
2. **打分只做了粗筛**。第一轮是「查询向量 vs 片段向量」，两边各自独立编码，
   只能判断「说的是不是一回事」，判断不了「这段到底有没有回答问题」。
   实测就有「关键词全中但答非所问」的片段排在高分位置。

## 决策一：追问先用模型补全，再检索

- 只在**会话内**、且**看起来像追问**时触发：
  问题长度 ≤ 12 字，或含「这 / 那 / 它 / 其 / 该 / 上面 / 刚才 / 还有 / 呢 / 同样」。
  独立问题（「Spring Boot 工程脚手架有什么」）不调用模型，省一次往返。
- 提示词只做一件事：补全。明确禁止回答、禁止加前缀、限制 40 字。
- 输出要清洗：去前缀、去引号、只取第一行、超 100 字丢弃、含「无法 / 抱歉」丢弃。
- 失败一律回退到原问题 —— 最差退化成改造前的行为。
- 改写结果**只用于检索**：回答与界面仍展示用户原话，落库时写进
  `ai_message.retrieval_query`（V14），后台问答记录里摊开显示。

实测：

| 原话 | 改写成 | 结果 |
|---|---|---|
| 那分块呢 | 站内有哪些关于 RAG 分块调优的实践记录？ | 命中分块章节 ✅ |
| 它的评估指标有哪些 | 分块策略的评估指标有哪些 | 命中评估章节 ✅ |
| 那它贵不贵 | 站内对 RAG 的 rerank 方案贵不贵？ | 正确理解为「方案成本」 ✅ |
| 那 RAG 手册呢 | RAG 手册包含什么？ | 识别为换话题，没有把上一轮对象拼进去 ✅ |

代价：追问多一次模型调用，DeepSeek V4.1（关思考）实测 0.6~1.2 秒。

### 多轮：历史用「已还原的问题」，而不是原话

只给上一轮是不够的：用户连着追问两轮后，「它」可能指向前两轮的主题。
现在带最近 3 轮（可配）进 prompt，但取的是 `COALESCE(retrieval_query, content)` ——
**上一轮如果也是追问，它的原话同样指代不清**，拿它当锚点等于在模糊上再猜一次；
改写后的句子才是能自洽的上下文。

### 答案侧：代词可能只出现在上一轮回答里

「站内有哪些技术方案？」→ 回答列了六篇 →「第一篇讲什么」。
这里的「第一篇」不在任何提问里，只存在于**回答**的结构中，只看提问补不出来。
现在把上一轮回答的前 180 字（可配，0 表示不用）拼进 prompt，并明确规则：
先看提问，提问里找不到再看回答，不许凭空编。

实测：同一会话里「第一篇讲什么」被改写成「《企业级 RAG 系统设计手册》讲什么？」，
引用与答案都对上了第一篇。

边界：**只带最近一轮回答**。「那第二篇呢」这类引用更早一轮列表的追问，
如果最近的回答里没有那个列表，仍会退化成「第二篇资料讲什么？」——
够检索，但不够精确。带多轮回答会让 prompt 翻倍，暂时不做。

### 「那 X 呢」的歧义要靠示例解决

第一版提示词只写了「补全代词与省略成分」，模型把「那 RAG 手册呢」改成了
「Spring Boot 脚手架中的 RAG 手册包含什么？」—— 把换话题当成了补方面。
补规则（X 是新对象就换话题）没用，加了三个 few-shot 示例才纠正。
这类歧义用例子比用规则描述有效得多。

## 决策二：重排做成可替换的三态，而不是绑死一个模型

`Reranker` 接口只收「查询 + 候选文本」，只回下标，与业务对象解耦。三种实现：

| provider | 说明 | 适用 |
|---|---|---|
| `none`（默认） | 不重排，保持第一轮顺序 | 只要基础可用性 |
| `llm` | 用对话模型做列表排序（输出编号数组） | 只有生成模型的部署（本项目当前） |
| `http` | 专用 rerank 服务（bge-reranker-v2-m3 等） | 有 Infinity / TEI / Jina / Cohere |

选 `llm` 的理由：排序是**相对判断**，模型对相对关系的判断远比绝对打分可靠；
一次调用排 20 条，比逐条判 yes/no 省得多。候选只送标题 + 160 字摘要，
重排看的是「这段讲的是不是这件事」，全文进 prompt 既贵又没必要。

选 `http` 的理由：真交叉编码器更准、更快，多部署一个服务而已。
这是部署决策，不是代码决策，所以做成配置。

### 截断：模型说「都不相关」是可以接受的结论

重排除了排序，还负责把噪音挡在外面：提示词要求「只输出与问题直接相关的编号」，
模型没列出的就等于无关。两道保险避免削得太狠：

1. **最少保留 `min-keep`（默认 2）条**：模型漏判时用原顺序补齐，
   免得「明明检索到了却答不出来」
2. **空结果看第一轮分数**：模型说全不相关时，如果首位候选原始分 ≥ `empty-keep-score`（0.5）
   仍保留最少条数，否则真的返回 0 条 —— 前者防模型过严，后者承认「站内确实没有」

实测「退款怎么处理」（站内没有退款内容）：从原来的 3 条无关引用变成 0 条，
问答直接回「站内暂时没有找到」，不再拿课程大纲硬答。

### 缓存：改写与重排都进 Redis

两条链路都是一次额外模型调用，重复提问不该重复花钱：

| 类别 | 键 | TTL | 说明 |
|---|---|---|---|
| 改写 | 历史 + 本轮问题 的摘要 | 1 小时 | 「判过不用改写」也缓存（哨兵值），避免反复调用 |
| 重排 | 策略版本 + 实现 + 问题 + **候选正文摘要** | 15 分钟 | 摘要覆盖标题与全文，内容一改就换键 |

实测同一搜索第二次 1056ms → 71ms。三个细节：

- **候选指纹取正文摘要，不取 docId:chunkIndex**：文章改了内容但块划分没变时 id 完全一样，
  用 id 做键会命中旧排序 —— 表现是「内容更新了，搜索结果还是按老文本排的」，且 15 分钟内反复出现。
  实测把某个块的内容改掉一个后缀后，首次搜索 315ms（重新重排）、之后 72ms（命中新键）。
- **键带策略版本**：改提示词或截断规则后旧排序不再适用，手动 +1 比等过期可靠
- **Redis 异常按未命中处理**：缓存是省钱手段，不该成为故障点

### http 重排的阈值：先归一化，再用相对下限

交叉编码器返回的分数有两套量纲：bge-reranker 是 logits（可负、范围因模型而异），
Jina / Cohere 是 0~1 相关度。直接填一个绝对阈值等于把某个模型的量纲写进配置。

两层处理，让它不需要标定也能用：

1. **归一化**：`ai.rerank.score-mode=auto` 时，出现负数或 >1 的值即判定为 logits，
   统一过 sigmoid 到 0~1；概率原样使用（`clamp` 到 0~1）
2. **相对下限**：`ai.rerank.relative-floor=0.5` —— 低于「首位分数 × 0.5」的候选丢弃。
   比例是跨模型可比的语义，不需要知道某模型的分数范围；
   如果候选都挤在高分区（0.8~0.9），说明它们同样相关，此时一条都不丢

绝对阈值 `ai.rerank.min-score` 仍保留（0~1 空间），但默认 0：
真要卡死一条线时再填，而不是当作常规手段。

### 配套的三条保护

1. **多取候选**：启用重排时第一轮取 20 条（可配），重排挑最终 6/8 条。
   只给最终条数，重排就无从纠正排序。
2. **失败回退原顺序**：排序差一点总比整页报错强。
3. **连续失败熔断 60 秒**：配置写错时不会有每个请求都白等一次超时。

（早期版本会把模型漏掉的编号补在末尾；启用截断后这条规则被 `min-keep` 取代：
补末尾等于让截断失效，而下限已经能保证上下文不被削空。）

## 效果（本地 bge-m3 + DeepSeek V4.1）

同一批查询，仅切换 `AI_RERANK_PROVIDER`：

| 查询 | 无重排 | 有重排 |
|---|---|---|
| RAG 检索要记录哪些调优过程 | Java 工程师的 AI 应用开发实战 → 企业 AI 应用定制 → **企业级 RAG 手册（第 3）** | **企业级 RAG 手册** → Java 工程师 → 企业 AI 应用定制 |
| 怎么搭一个 Spring Boot 项目骨架 | Spring Boot 4 脚手架 → **Java 工程师（不相关，第 2）** | Spring Boot 4 脚手架 → **Spring Boot + MyBatis（第 2）**，Java 工程师退到第 5 |

代价：搜索 231~344ms → 612~1059ms（含重排调用）。聊天总时长 2.5~3.1 秒
（改写 + 检索 + 重排 + 生成），首字节 1.4~1.7 秒。

## 没做的

- **多轮回答上下文**：只带最近一轮回答。「那第二篇呢」若指向更早一轮的列表，
  仍会退化成泛化改写。带多轮回答会让 prompt 翻倍，暂时不做。
- **相对下限的系数**：0.5 是经验值，业务上更怕漏还是更怕噪音，应由使用方定。
- **改写缓存与索引的一致性**：改写只看对话文本，与索引无关，所以索引更新不需要失效它；
  但模型换了（`AI_LLM_MODEL`）理论上应失效，目前靠 1 小时 TTL 兜。
