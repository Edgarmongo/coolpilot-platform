# PRD：个人技术知识与服务平台（V1.0 – V1.2）

> 版本：v1.0 草案
> 日期：2026-11-04
> 基线：三端项目（Spring Boot 4.1.2 + Vue 3 / Nuxt 前台 + MySQL 39 表）
> 范围：V1.0 内容与社区 / V1.1 知识付费 / V1.2 技术服务与需求
> 不含：V1.3 AI 智能中心、V2.0 学习体系与用户运营（仅预留）

---

## 一、产品定位

**个人技术知识与服务平台** —— 一个平台所有者 + 多个普通用户 + 多种知识产品 + 多种技术服务。

不是多创作者内容平台，不是开放式技术服务交易市场。平台所有者是唯一的内容生产者、商品提供者、服务提供者和运营者。

### 1.1 建设边界（防止业务膨胀）

| 能力 | 是否建设 | 说明 |
|---|---|---|
| 个人技术博客 / 内容中心 | ✅ | 流量入口 |
| 知识付费（文档/课程/专栏/代码） | ✅ | 标准化收入 |
| 技术服务销售 | ✅ | 高客单价收入 |
| 客户需求发布 | ✅ | 主动商机 |
| 用户评论 / 收藏 / 点赞 | ✅ | 留存与传播 |
| AI 知识问答 | ⏳ V1.3 | 差异化能力 |
| 多创作者入驻 | ❌ | 创作者只有 OWNER |
| 多服务商入驻 | ❌ | 不做开放服务市场 |
| 用户之间交易 | ❌ | 不做撮合 |
| 自动分账 / 资金托管 | ❌ | 初期不需要 |
| 直播 / 会员订阅制 | ❌ | 不在 V1 范围 |

### 1.2 三条业务主线

| 主线 | 目标 | 关键指标 |
|---|---|---|
| 内容引流 | 让技术人员找到并信任平台 | 自然搜索流量、文章阅读量、收藏率 |
| 知识变现 | 把经验转成可重复销售的数字产品 | 商品转化率、客单价、复购率 |
| 服务变现 | 把技术能力包装成可购买的服务 | 需求数、报价转化率、交付周期 |

## 二、角色与权限

### 2.1 角色模型

业务身份只有两类，不引入"创作者/服务商"等中间角色。

| 角色 | 数量 | 说明 |
|---|---|---|
| `OWNER` | 1（唯一） | 平台所有者，全部管理权限 |
| `USER` | N | 普通用户，消费 + 互动 + 下单 |

> **实现建议**：V1 阶段不建 `role` / `permission` 独立表，沿用现有 `user.role` 字段（`ROLE_owner` / `ROLE_user`）。三层权限用「前端路由白名单 + Security 接口规则 + 权益表」表达即可，详见《DATA-MODEL.md》决策 D2。

### 2.2 权限矩阵

| 操作 | OWNER | USER | 控制层 |
|---|---|---|---|
| 发布 / 编辑 / 下架文章 | ✅ | ❌ | 接口 |
| 查看公开文章 | ✅ | ✅ | — |
| 查看付费内容 | ✅ | 购买后 ✅ | 资源（entitlement） |
| 创建知识商品 | ✅ | ❌ | 接口 |
| 购买知识商品 | ✅ | ✅ | — |
| 创建服务商品 | ✅ | ❌ | 接口 |
| 提交技术服务需求 | ✅ | ✅ | — |
| 查看全部订单 | ✅ | ❌ | 接口 |
| 查看自己的订单 | ✅ | ✅ | 资源（owner_id 校验） |
| 下载付费文件 | ✅ | 有权益才 ✅ | 资源（签名 URL） |
| 评论 / 收藏 / 点赞 | ✅ | ✅ | — |
| 用户管理 / 评论审核 | ✅ | ❌ | 接口 |

**红线**：任何接口都必须校验「资源归属」，不能只靠前端隐藏。用户改 URL 或改 `id` 参数不能读到他人的订单、需求、私有文件。

| 分类管理 | 增删改查、排序、图标 | ⚠️ 仅有名称 | 小（加字段） |
| 标签管理 | 增删改查、颜色 | ✅ 已有 | 复用 |
| 专题管理 | 专题创建、文章编排、排序、封面 | ❌ 缺 | 中 |
| 教程管理 | 系列教程、章节、学习顺序 | ❌ 缺 | 大（V1.0 后段） |
| 技术动态 | 短内容发布、点赞 | ⚠️ moment 已有，缺"项目进度"分类 | 小 |
| 评论管理 | 审核、回复、删除 | ✅ 已有 | 复用 |
| 内容统计 | 浏览量、收藏量、点赞量、转化率 | ⚠️ 仅浏览量 | 中 |

**核心要求**

|---|---|---|---|

| 收藏 | ✅ | ✅ | ❌ 缺 |

**个人中心页面清单（新增）**
`/me`（概览）· `/me/orders` · `/me/courses` · `/me/favorites` · `/me/comments` · `/me/demands` · `/me/settings` · `/me/messages`

**验收标准（V1.0）**
1. 访客可注册、登录、退出，登录态在刷新后保持
2. 可收藏文章、点赞动态，个人中心能看到自己的收藏与评论

4. 文章支持 slug 访问，旧 id 链接不 404
5. 后台可查看每篇文章的阅读/收藏/点赞/转化数据
6. 普通用户无法访问任何 `/admin/**` 接口（已满足，回归验证即可）

## 五、V1.1：知识付费中心

目标：跑通「浏览 → 下单 → 支付 → 发放权益 → 交付 → 可退款」完整闭环。

### 5.1 商品形态

| 类型 | 说明 | 交付形态 |
|---|---|---|
| 付费文档 `DOC` | 架构设计、部署手册、解决方案、开发规范 | PDF / Markdown / ZIP 下载 |
| 视频课程 `COURSE` | 章节 + 课时，支持试看 | 在线播放 + 学习进度 |
| 知识专栏 `COLUMN` | 持续更新的文章集合 | 站内阅读（关联 blog） |
| 代码资源 `CODE` | 源码、脚手架、模板、脚本 | ZIP 下载 / 仓库授权，支持版本更新 |

### 5.2 功能清单

| 模块 | 功能点 |
|---|---|
| 商品管理 | 创建、编辑、上下架、排序、封面、详情富文本 |
| 商品分类 | 文档 / 课程 / 专栏 / 代码资源 |
| 商品定价 | 固定价、划线原价、限时优惠（开始/结束时间） |
| 前台商品页 | 列表、详情、目录预览、试看、购买按钮、已购标识 |
| 订单 | 创建、待支付、取消、超时关闭、查询 |
| 支付 | 渠道选择、支付单、回调验签、幂等、对账 |
| 权益 | 购买发放、退款撤销、有效期、权限校验 |
| 交付 | 文件下载（授权 + 短时签名）、课程访问、资源版本更新 |
| 售后 | 退款申请、审核、退款执行 |
| 统计 | 销售额、订单量、客单价、转化率、退款率 |

### 5.3 关键业务规则

| 编号 | 规则 |
|---|---|
| R1 | 商品与文章分离。付费专栏通过 `product_article` 关联文章，文章本身仍可公开或部分公开 |
| R2 | 下单即锁定价格快照（`order_item.price_snapshot`），后续改价不影响历史订单 |
| R3 | 订单 30 分钟未支付自动关闭（可配置） |
| R4 | 支付回调必须幂等：以 `payment.trade_no` 唯一索引 + 状态机双重保护 |
| R5 | 权益发放以「支付成功回调」为唯一触发点，不依赖前端跳转 |
| R6 | 退款按商品规则：`DOC/CODE` 下载后不可退；`COURSE/COLUMN` 学习进度 < 20% 可退（规则可配置） |
| R7 | 退款成功必须同步撤销权益，并写 `entitlement_log` |
| R8 | 付费文件不暴露永久 URL，下载必须走后端鉴权 + 短时签名 |
| R9 | 同一用户对同一商品重复下单需拦截（已有有效权益时提示"已购买"） |

### 5.4 验收标准（V1.1）

1. OWNER 可创建 4 类商品并上架，前台可见
2. 用户下单 → 支付成功 → 立即获得权益 → 能访问内容，全流程无人工干预
3. 同一支付回调重复推送 5 次，订单状态与权益数量不变（幂等验证）
4. 未购买用户直接访问付费内容 URL，返回 403 而非内容
5. 退款审核通过后，权益自动撤销，用户再次访问被拒
6. 后台能按商品维度看到销售额、订单量、退款率

## 六、V1.2：技术服务 + 需求中心

目标：把"接私活"过程产品化，形成可追踪的商机到交付链路。

### 6.1 服务商品（OWNER 创建，USER 购买）

| 服务类别 | 示例 |
|---|---|
| Java 后端开发 | API 开发、业务模块、系统维护 |
| 系统部署运维 | Linux / Docker / MySQL / Redis 部署 |
| AI 应用开发 | RAG、知识库、Agent、模型接入 |
| 企业 AI 集成 | 内部 AI 助手、业务系统集成 |
| 技术咨询 | 技术选型、架构评估、项目诊断 |
| 项目定制 | Java 系统、AI 应用定制 |

**三种定价方式**（必须都支持）

| 方式 | 适用场景 | 下单行为 |
|---|---|---|
| 固定价 `FIXED` | 标准化部署、单次咨询 | 可直接下单支付 |
| 起步价 `STARTING` | 需评估后确定工作量 | 下单后进入需求评估，不直接全额支付 |
| 定制报价 `CUSTOM` | 企业级开发 | 只能提交需求，由 OWNER 报价 |

> **关键**：定制类服务**不允许**"付款即自动交付"。必须有需求评估 → 报价 → 确认三个环节。

### 6.2 需求中心（USER 主动发起）

| 字段 | 说明 |
|---|---|
| 项目类型 | 后端开发 / AI 应用 / 部署运维 / 咨询 / 其他 |
| 技术要求 | 技术栈、规模、集成要求 |
| 预算区间 | 最小/最大，可填"面议" |
| 期望交付时间 | 日期 |
| 需求描述 | 富文本 + 附件 |
| 联系方式 | 手机/微信/邮箱（仅 OWNER 可见） |

### 6.3 状态机

**需求 `demand.status`**

```
PENDING_REVIEW → PENDING_CONTACT → EVALUATING → PENDING_QUOTE
      → PENDING_CONFIRM → IN_PROGRESS → PENDING_ACCEPT → COMPLETED
异常：REJECTED / CANCELLED / DISPUTED
```

**服务订单 `service_order.status`**

```
PENDING_PAY → PAID → IN_PROGRESS → PENDING_ACCEPT → COMPLETED → AFTER_SALE
异常：CANCELLED / REFUNDED
```

**项目 `project.status`**：`NOT_STARTED → IN_PROGRESS → PENDING_ACCEPT → COMPLETED → ARCHIVED`

**里程碑 `milestone.status`**：`PENDING → DELIVERING → DELIVERED → ACCEPTED`（可 `REJECTED` 打回）

### 6.4 验收标准（V1.2）

1. 用户可提交需求（含附件），后台可见并审核
2. OWNER 可对需求报价，用户可确认或拒绝
3. 确认后自动生成项目与首个里程碑
4. 里程碑交付后可上传交付物，用户可验收/打回
5. 全流程每个状态变更都有操作记录（谁、何时、从什么状态到什么状态）
6. 用户只能看到自己的需求与项目

## 七、三条核心商业闭环

### 流程 A：内容 → 知识付费

```
搜索/外部链接 → 免费文章 → 收藏/评论 → 文章底部推荐付费专题
→ 商品详情 → 下单 → 支付 → 权益 → 进入课程/下载 → 复购
```

**系统落点**：文章详情页需挂载"关联商品"组件；`product_article` 提供关联；用户有权益时按钮态为「已拥有」。

### 流程 B：技术服务成交

```
技术服务页 → 选择服务商品 → 提交需求（或直接下单）
→ OWNER 评估 → 报价 → 确认 → 支付 → 实施 → 交付验收 → 售后
```

**系统落点**：`service_item.price_mode` 决定走「直接下单」还是「必须走需求」。

### 流程 C：客户主动提需求

```
提交需求 → 后台审核 → 沟通 → 评估 → 报价 → 建项目 → 里程碑 → 验收
```

**系统落点**：需求与项目可 1:1，也可一个需求拆多个项目（`project.demand_id` 非唯一）。

## 九、对原始蓝图的 7 处修正建议

| # | 蓝图原设计 | 问题 | 建议 |
|---|---|---|---|
| 1 | 表名 `Order` | `ORDER` 是 MySQL 保留字，每次都要反引号，ORM 易出错 | 改名 `orders` |
| 2 | 建议建 `User / Role / Permission` 三表 | 只有两种角色，建三表是过度设计，且与现有 `user.role` 冲突 | V1 用角色枚举；真正的"资源权限"交给 `entitlement` |
| 3 | 商品统一 `Product` + 各类型扩展 | 方向正确，但漏了「专栏 = 文章集合」的关联表 | 补 `product_article` |
| 4 | 服务订单独立于商品订单 | 两张订单表会导致对账分散 | 保留独立 `service_order`，但**支付/退款统一走 `payment` / `refund`**，通过 `biz_type` 区分 |
| 5 | AI 检索按内容权限隔离 | 只说"要隔离"，没给机制 | 复用 `entitlement` 做 chunk 级过滤，检索前先取用户可访问商品集合 |
| 6 | 文件下载"不暴露永久地址" | 未说明实现方式 | 后端签发 5 分钟有效的临时 token，`/file/download?token=` 校验后流式返回 |
| 7 | 需求与项目关系 | 未定义 1:1 还是 1:N | 定为 1:N（`project.demand_id` 非唯一），支持一个大需求拆多期 |
