# ADR-0002：混合检索与向量模型切换

- 状态：已采纳（2026-11-05）
- 前置：ADR-0001（向量存 MySQL、进程内余弦、`EmbeddingClient` 接口）

## 背景

ADR-0001 落地时用的是本地哈希向量（`hash-ngram-512`），它解决的是「没有模型也能检索」，
本质仍是**字面召回**：问法和原文用词对不上就找不到。比如站内文章写「工程脚手架」，
用户问「怎么搭项目骨架」，命中率依赖重合的词。

有了可用的向量模型（本地 Ollama 的 `bge-m3`，1024 维）之后，需要回答两个问题：

1. 怎么在不改存储、不引向量库的前提下换成语义向量？
2. 纯语义检索对「型号、专有名词、精确短语」反而变弱，怎么补？

## 决策

### 1. 新增一个 `EmbeddingClient` 实现，按配置切换

```
ai.embedding.provider = hashing | openai
```

- `hashing`：原有实现，默认值，离线/CI 可用，维度 512
- `openai`：任意 OpenAI 兼容 `/embeddings` 端点（Ollama / vLLM / DeepSeek / 通义 / OpenAI）

两者靠 `@ConditionalOnProperty` 二选一，业务代码只依赖接口。
`kb_chunk` 早已存了 `dim` 与 `model`，切换模型后旧向量会被检索侧跳过，
后台 `stats.ignoredChunks` 会显示「有多少块需要重建」，不会拿错向量硬算。

**换 provider 或 dim 必须重建索引**，这是这套设计唯一的操作约束。

### 2. 混合打分：向量 + 字面覆盖率

```
score = alpha × cosine(query, chunk)
      + (1 - alpha) × 字面证据            // 正文覆盖率与标题覆盖率取大者
      + titleBoost × 标题覆盖率            // 标题是「这段讲什么」的最强信号
```

- `alpha` 默认 0.65：语义为主，关键词兜底
- 字面证据用「查询词在正文/标题里的覆盖率」，中文按「二字词优先、单字兜底」切分（`TextTokenizer`）
- 不做 TF-IDF：语料只有几百块，IDF 估不准，反而让常见词权重失真

### 3. 阈值分两层，而不是一个 min-score

语义模型的余弦普遍偏高（bge-m3 对任意中文短句也有 0.3~0.45），
沿用哈希时代的 `min-score=0.05` 会把无关问题也检出 8 条。于是：

- `semantic-floor`（默认 0.5）：**完全没有字面证据**时，向量必须更相似才认
- `min-score`（默认 0.25）：最终得分的下限

## 后果

- 检索质量：同义改写能召回（「怎么搭项目骨架」正确命中「Spring Boot 4 工程脚手架」并排第一）；
  无关问题（「今天天气怎么样」）基本不再刷出一屏结果
- 代价：语义模型调用会给每次检索加几十毫秒；模型服务不可用时自动降级为纯字面检索（不报错）
- 重建索引从「每块一次请求」变成「每批一次」（`ai.embedding.batch-size`，默认 16）
- 已知取舍：标题/正文完全不含查询词、且语义相似度低于 0.5 的文档会被丢掉，
  这比「返回一堆不相干结果」更符合搜索的预期

## 补充：同文档取多块（2026-11-06）

原实现对每个文档只保留**一个**最像的块。文档一长就出问题：问「状态管理用什么」，
最像的块可能是「性能」那一段，而「全局状态（Pinia）」在相邻块里 —— 模型只会说「资料没提到」。

改成默认取每篇得分最高的 2 块，按 `chunkIndex` 顺序拼成一段（上限 650 字）：

- 按原文顺序而不是分数顺序拼：上下文要能顺读，分数顺序会让段落跳来跳去
- 上限内剩余空间不够 80 字就停：宁可少给，也不要拼出半句话
- 引用编号仍是「一篇一个」，不会出现同一标题两条引用
- `ai.search.chunks-per-doc=1` 可回到旧行为

实测同一问题：「Vue 大型项目的状态管理推荐用什么」原来答「站内资料没有提到」，
现在答「推荐用 Pinia，并配合 TanStack Query 处理接口数据」，引用与正文一致。
