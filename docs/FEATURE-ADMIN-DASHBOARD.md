# 后台仪表盘：功能梳理

> 梳理日期：2026-11-21 ｜ 依据 `v1.1.3` 线上代码
> 涉及：`coolpilot-admin/src/views/dashboard/index.vue`、`TradeAdminController`、`OrderService`、`PaymentService`

## 一、定位

后台登录后的默认落地页（`/` → `/dashboard`），回答一个问题：

> **今天有没有钱进来、有没有事要处理。**

它**不是**站点流量看板。PV / UV / 分类分布 / 访客城市这些统计仍留在后端，但界面已经不再展示（见 §6）。

## 二、页面结构

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│  累计销售额   │    净收入     │   退款金额    │  待确认收款   │
```

一次加载两个接口（`Promise.all` 并发），右上角「刷新」按钮手动重拉，**没有自动轮询**。

| 区块 | 接口 | 参数 |

| 四个统计卡 | `GET /admin/stats/sales` | 不传时间，即全量 |
| 最近订单 | `GET /admin/orders` | `pageNum=1&pageSize=5` |
| 待确认角标 | 同上销售的 `waitingConfirm` | — |

## 三、四个指标的口径

### 1. 累计销售额 `paidAmount`

```sql
SELECT IFNULL(SUM(pay_amount), 0) FROM orders
WHERE status IN ('PAID', 'COMPLETED', 'REFUNDING', 'REFUNDED')
```

- **含已退款订单**（页面上也标了这行提示）
- 用 `pay_amount` 而非 `total_amount`，即扣掉优惠后的实付
- 时间字段是 **`create_time`**（下单时间）

> 含义是「历史上收进来过多少钱」，不是「现在账上有多少钱」。

### 2. 净收入 `netAmount`

```
netAmount = paidAmount − refundAmount
```

后端直接算，前端不参与。这是唯一能看「实际赚了多少」的数。

### 3. 退款金额 `refundAmount`

```sql
SELECT IFNULL(SUM(amount), 0) FROM refund
WHERE status = 'SUCCESS'
```

- **只算已完成的退款**（`SUCCESS`）；`PENDING` / `APPROVED` 还没打款，不计入
- 时间字段是 **`refund_time`**（退款完成时间）

### 4. 待确认收款 `waitingConfirm`

```sql
SELECT COUNT(*) FROM payment WHERE status = 'WAIT_CONFIRM'
```

- 数的是**支付单**，不是订单

## 四、最近订单列表

| 列 | 来源 |
|---|---|
| 订单号 | `orders.order_no` |
| 内容 | `titleSummary`：把该单所有明细标题拼起来，多于 1 件显示「… 等 N 件」 |
| 金额 | `orders.pay_amount`，前缀 ¥ |
| 状态 | 8 个状态的中文映射 + 标签颜色 |

- 排序：`ORDER BY o.id DESC`，即**按建单先后倒序**，取前 5 条
- 明细是批量查的（`listByOrderIds`），5 条订单只有 1 次附加查询，不是 N+1
- 表头右侧「全部订单 →」跳 `/trade/order`

## 五、待办区（三个入口）

| 入口 | 跳转 | 说明文案 |
|---|---|---|
| 待确认收款 | `/trade/order?status=PENDING_CONFIRM` | 用户已提交转账凭证，核对后确认即发权益（带未处理数量角标） |
| 退款处理 | `/trade/refund` | 同意申请 → 线下打款 → 确认后撤销权益 |
| 权益管理 | `/trade/entitlement` | 人工发放、撤销与流水核查 |

这三个链接指向的是**需要人工介入的环节**，也就是当前「人工收款 + 人工退款」模式下最容易堵住的地方。

## 七、六个值得注意的问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **两个金额的时间口径不同**：销售额按 `create_time`，退款按 `refund_time` | 一旦按日期筛选，跨期退款会被算进错误的区间，净收入会失真 | 统一改成「按下单时间归属」，或两个指标都提供口径说明 |
| 2 | **前端没有日期筛选**，接口却支持 `startTime` / `endTime` | 只能看全量，"这个月赚了多少"看不到 | 加一个时间范围选择器，接口现成 |
| 3 | **销售额含已退款**，与「净收入」并排展示 | 容易误读成"赚了这么多" | 已加提示文字，可考虑把净收入放第一张卡 |
| 4 | `waitingConfirm` 数的是支付单，待办链接筛的是订单状态 | 正常情况下两者同步（提交凭证时两表一起改）；异常时序下会不等 | 保持现状，异常时以支付单为准（它才是钱的那一侧） |
| 5 | **没有自动刷新** | 长时间开着页面看到的是旧数据 | 低优先，需要时手动刷新即可 |
| 6 | 没有权限细分 | 所有 `ROLE_owner` 都看到全部数字 | 当前只有一个账号，无需处理 |

## 九、如果要改，建议顺序

1. **加时间范围筛选**（接口已支持，只改前端）—— 这是「知道这个月赚多少」的最低成本方案
2. **统一金额的时间口径** —— 否则筛选一上线，数字就会互相矛盾
3. 把 `PV / UV` 作为第二屏接回来（后端现成，加一个「站点流量」Tab 即可）
4. 待办角标扩展到「退款待处理」「超时未支付订单」
