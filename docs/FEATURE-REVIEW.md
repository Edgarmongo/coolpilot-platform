## 一、评审方法

### 1.1 每个功能按 15 个维度过一遍

| 维度 | 要回答的问题 |
| --- | --- |
| 功能名称 | 到底是什么 |
| 所属业务域 | 哪个域 |
| 用户角色 | 访客 / 注册用户 / 站长 |
| 用户价值 | 解决什么问题 |
| 入口 | 从哪里进得来 |
| 可见内容 | 能看到什么 |
| 可执行操作 | 能做什么 |
| 权限限制 | 谁不能做 |
| 状态约束 | 不同状态下允许什么 |
| 数据依赖 | 依赖哪些表 / 接口 / 模块 |
| 异常情况 | 失败、空数据、重复操作怎么办 |
| 当前问题 | 已知缺陷与不足 |
| 决策 | 保持 / 优化 / 修改 / 暂缓 / 废弃 |
| 优先级 | P0–P3 |
| 证据 | 源码位置、实测数字、报告 |

### 1.2 决策图例

| 决策 | 含义 | 触发条件 |
| --- | --- | --- |
| **保持** | 不改，纳入基线 | 功能有效、成本合理 |
| **优化** | 不动结构，改内容或体验 | 功能对，但呈现不到位 |
| **修改** | 有缺陷 / 口径不一致，需改代码或数据 | 用户完成不了任务，或数据对不上 |
| **暂缓** | 保留能力，等条件成熟再评审 | 依赖内容量或用户量 |
| **废弃** | 下线，从导航与 sitemap 移除 | 无人使用且无间接价值 |

### 1.3 优先级

| 级别 | 含义 |
| --- | --- |
| **P0** | 本周内处理：影响资金、数据一致性或可被搜索引擎判为低质 |
| **P1** | 本期（两周）处理：影响转化或可发现性 |
| **P2** | 下期：体验优化 |
| **P3** | 不做，记录理由，避免反复讨论 |

### 1.4 证据规则

**每条结论必须附证据**，三类之一：源码位置（`文件:行`）、实测数字（接口/数据库/耗时）、已有文档（ADR）。
没有证据的判断标「待验证」，不写进决策。

## 二、价值分层

| 层 | 域 | 判断标准 |
| --- | --- | --- |
| **L1 内容获客** | 内容与阅读、开源观察、作品集 | 用户能否发现你、判断你的能力 |
| **L2 价值变现** | 知识商品、交易 | 用户能否买到、拿到、退得掉 |
| **L3 业务交付** | 技术服务 | 需求能否变成可验收的交付 |
| **L4 平台支撑** | AI 问答、账号与社区、运营与系统 | 检索、身份、运维是否撑得住 |

评审任何功能先问三句：**服务哪一层？删掉会怎样？有没有替代路径？**

## 五、冻结规则

1. 一个域评审完成即**冻结**：结论写入本文第四节，明细留在域文档。
2. 冻结后如需推翻结论，新开一条「复议」记录，写清：依据什么新证据、影响哪些已冻结项。
3. 每次改动代码，若影响已冻结的结论，必须同步更新域文档的「决策」列，否则视为文档失效。
4. **未评审的域不做功能开发**——避免边评审边改，结论互相打架。

## 六、总体观察（DOMAIN-01 之后）

评审一个域之后，最需要先摆到台面上的是这个落差：

| 项 | 数量 |
| --- | --- |
| 前台页面 | 34 个 |
| 线上真实内容 | **1 篇文章 · 1 个作品集 · 0 商品 · 0 专题 · 0 动态 · 0 友链** |
| 后台管理页 | 32 个 |

也就是说：**平台按「有内容在运营」的规模建，实际按「刚起步」的状态使用。**
这不是功能缺陷，但它决定了接下来所有优先级——在内容补上之前，新增功能对用户的边际价值接近于零。

这条观察会贯穿后面 8 个域的评审，每一域都要回答同一个问题：
**这个功能现在没有内容喂它，是保留、隐藏，还是先下线？**

## 七、文档体系

评审结果不覆盖事实基线，两者的分工写在 [docs/README.md](README.md)：

| 文件 | 角色 |
| --- | --- |
