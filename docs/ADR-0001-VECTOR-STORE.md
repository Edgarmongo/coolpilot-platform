# ADR-0001：V1.3 知识库的向量存储与 Embedding 方案

- 状态：已采纳（2026-11-05）
- 背景：V1.3 要做「站内知识库 + 带引用的检索问答」，需要向量检索与 Embedding 模型

---

## 1. 约束

| 约束 | 说明 |
|---|---|
| 服务器规格 | 2C4G，已经有 MySQL / Redis / api / web / admin / gateway 六个容器 |
| 语料规模 | 个人站点量级：文章 + 商品文案 + 课时，预计 **1e3 ~ 1e4 个块** |
| 权限是硬需求 | 付费课时的内容不能出现在未购买用户的检索结果里 |
| 外部依赖 | 现阶段没有可用的 Embedding API Key，开发/CI 必须能离线跑 |
| 可替换性 | 以后可能换 Milvus / Qdrant，业务代码不应被写死 |

## 2. 候选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Milvus** | 功能全、生态好 | 依赖 etcd + MinIO，内存起步 4G，本机都吃力 | ❌ |
| **Qdrant** | 单容器、轻量、payload 过滤 | 多一个服务；权限数据要同步进 payload，跨系统一致性要自己维护 | 暂不 |
| **pgvector** | 与 PG 集成好 | 现有库是 MySQL，等于再引入一套数据库 | ❌ |
| **外部向量服务** | 免运维 | 数据出境、按量计费、可用性绑定第三方 | ❌ |
| **MySQL 存向量 + 进程内暴力检索** | 零新增组件；权限过滤就是一条 SQL/JOIN；语料规模下延迟毫秒级 | 规模上到百万块会退化 | ✅ 第一阶段 |

**关键算术**：1e4 块 × 512 维 × 4B ≈ 20MB 常驻内存；单次检索做 1e4 次点积 ≈ 5e6 次乘加，单核几毫秒。
在这个量级上引入独立向量库，运维成本远大于性能收益。

## 3. 决策

1. **向量存 MySQL**：`kb_chunk.embedding`（`MEDIUMBLOB`，float32 小端）+ `dim` + `model`。
   进程内维护一份「块 + 向量」快照，重建索引后失效，其余时间直接内存检索。
2. **权限在装载阶段过滤**，而不是检索后过滤：快照里每块带 `is_public` 与 `product_id`，
   检索时用「公开 或 已购商品集合」筛选候选，从源头杜绝越权召回。
3. **Embedding 走接口**：`EmbeddingClient`，当前实现 `HashingEmbeddingClient`（字符 n-gram 哈希，离线、确定性）。
   配置 `ai.embedding.provider` 后可接入远程模型，接口不变。
4. **保留替换路径**：检索入口 `AiSearchService` 内部把「候选召回」与「打分」分开，
   将来换 Qdrant 只替换召回实现，Controller 与前端不用动。

## 4. 后果

- 正面：不增加容器；权限过滤简单可靠；离线可测；上线即可用。
- 负面：哈希向量的语义能力弱于真实模型，只能做「字面相近」的召回；
  真正做问答还需要接 LLM，这一步先把「检索 + 引用」打通。
- 触发迁移的条件：块数 > 5e4，或需要多租户/多知识库隔离，或需要按向量做聚合分析。

## 5. 落地范围（第一阶段）

| 项 | 内容 |
|---|---|
| 表 | `kb_knowledge_base` / `kb_document` / `kb_chunk`（V7） |
| 索引对象 | 已发布文章（跳过密码文章）、上架商品文案、课时正文（付费，带 product_id） |
| 接口 | `GET /ai/search?q=`（公开）、`POST /admin/ai/reindex`、`GET /admin/ai/stats` |
| 前端 | 搜索页增加「智能检索」区，结果带来源与相关度 |
| 不做 | 对话式问答（等 Embedding/LLM Key）、多知识库管理界面 |
