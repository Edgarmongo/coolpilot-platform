## 0. 前置说明：本次设计的三个原则

1. **现有业务能力优先复用**，不重复建设业务系统。
2. **统计数据必须有真实的数据来源和明确的计算口径**。
3. 先完成**数据可信、业务可视、待办可处理**，再引入 AI 分析。

**另有一项财务口径在此提前冻结**：

> 退款按**退款实际完成时间**进入退款发生期间，**不得**为了"统一"而改成订单下单时间。
> 成交金额则按**支付确认时间**归属。两者都是资金实际发生的时间，因此可以相减。

## 1. 项目背景

### 1.1 现状

当前后台仪表盘已从早期博客统计页演变为销售数据页，前端只消费：

- `GET /admin/stats/sales`
- `GET /admin/orders?pageSize=5`

旧 `/admin/dashboard`（PV / UV / 分类分布 / 城市统计）仍存在但**无前端消费者**，属遗留能力。

现有不足：

1. 只关注交易，无法反映全平台经营情况。
2. 没有统一时间范围筛选。
3. 缺少经营趋势与同期对比。
4. 缺少内容运营分析。
5. 缺少用户增长与活跃分析。
6. 缺少商品经营分析。
7. 缺少技术服务需求与交付进度统计。
8. 缺少统一业务待办中心。
9. 缺少真实的平台运行状态监控。
10. 尚未形成内容、用户、商品、交易、服务之间的经营分析链路。

### 1.2 重构目标

将仪表盘升级为 **CoolSkyAI 全平台经营管理驾驶舱**。

### 1.3 产品目标

| 目标 | 说明 |
|---|---|
| 经营可视化 | 收入、交易、用户增长 |
| 内容可视化 | 内容生产、访问、商业转化 |
| 用户可视化 | 规模、活跃度、付费情况 |
| 商品可视化 | 销售表现与商品结构 |
| 服务可视化 | 需求、报价、项目、交付状态 |
| 业务可执行 | 集中发现和处理待办 |
| 系统可观测 | 基础设施与关键链路状态 |

### 1.4 非目标

本期不建设：独立 BI 平台、企业级数据仓库、自助 SQL 分析、实时流式计算、AI 自动经营决策、多租户驾驶舱、独立 CRM/ERP。

## 3. 页面功能需求

### 3.0 公共区域

顶部提供：页面标题、时间范围、自定义起止时间、数据更新时间、手动刷新、加载状态、异常提示。

**统一时间筛选**：今日 / 昨日 / 最近 7 天 / 最近 30 天 / 本月 / 上月 / 自定义。默认**最近 30 天**。

时区固定 `Asia/Shanghai`（以部署配置为准）。

所有区间**左闭右开**：`[startTime, endTime)`，避免相邻区间重复统计。

### 3.1 D01 经营总览

| 指标 | 计算规则 |
|---|---|
| 成交金额 | 统计期间**支付确认时间**落入期间的有效成功支付金额 |
| 实际净收入 | 期间成交金额 − 期间成功退款金额 |
| 退款金额 | 统计期间**退款成功时间**落入期间的成功退款 |
| 待确认收款 | 当前等待人工确认的支付单数量（快照，非期间量） |
| 新增订单 | 统计期间**创建**的订单数量（含未支付） |
| 客单价 | 期间成交金额 ÷ 期间成功支付订单数 |

补充：成交订单数、环比/同比、退款率、付费用户数、最近订单列表。

**趋势图**：成交金额 / 退款金额 / 净资金流入 / 成交订单数。

粒度按跨度自动选择：≤1 天→小时；≤31 天→日；≤90 天→日或周；>90 天→月。

趋势必须使用真实统计结果，**不生成模拟数据**。

### 3.2 D02 内容运营

核心指标：内容总数、已发布数、期间新增、累计浏览量、期间浏览量、独立访客数。

排行榜字段：标题、类型、期间 PV、期间 UV、发布时间、状态。

分析项：浏览趋势、发布趋势、分类访问分布、热门文章 TOP10、内容与商品关联、内容到购买转化。

> **转化分析必须建立可验证的来源关联，不得将页面浏览量等同于商品转化量。**

### 3.3 D03 用户运营

核心指标：用户总数、新增、活跃、回访、付费用户、付费转化率。

图表：增长趋势、新老用户比例、活跃趋势、付费趋势、来源分布。

列表：最近注册、最近活跃、最近付费。

**统计定义**：

- 注册用户以账户创建记录为准。
- **活跃用户必须定义有效活动行为**，不能用注册数或 PV 替代。
- 回访用户用访客标识去重，须明确回访周期。
- 付费用户按至少一笔有效成功支付去重；退款是否影响身份需单独说明，**不得与金额口径混用**。

### 3.4 D04 商品运营

商品类型：AI 应用课程、技术文档、代码资源、知识产品、技术服务。

指标：商品总数、在售数、期间销量、成交金额、退款金额、退款率、访问量、购买转化率。

排行：销量 / 销售额 / 访问量 / 转化率 TOP10。

**所有商品统计必须依据订单商品明细与实际支付记录，不得用商品当前价 × 数量推算历史收入。**

转化率需商品访问事件与订单明细之间存在可靠的用户/访客关联。

### 3.5 D05 服务交付

复用现有链路：需求提交 → 报价 → 项目 → 里程碑 → 交付。

指标：新增需求、待响应、待报价、待确认报价、进行中项目、待交付项目、逾期里程碑、已完成项目。

近期业务事项：最新需求、待报价、待确认报价、即将到期里程碑、已逾期里程碑、等待验收交付。

每条须提供跳转入口。**待办数量必须与对应业务模块使用同一状态定义与筛选条件。**

### 3.6 D06 待办与系统健康

**业务待办**：待确认收款、待处理退款、待响应需求、待确认报价、待处理交付、逾期里程碑。

展示：名称、数量、优先级、最早发生时间、处理入口。

采用实时查询或短时缓存，**不得使用过期统计结果误导操作人员**。

**系统健康**：

| 检查项 | 监控内容 |
|---|---|
| Java API | 健康检查、响应状态 |
| MySQL | 连接及查询状态 |
| Redis | 连接状态 |
| 文件存储 | 可用性与磁盘容量 |
| AI 服务 | 已配置服务的可用性 |
| Quartz | 最近任务执行状态 |
| 支付链路 | 回调异常、待处理支付 |
| 应用异常 | 最近错误与趋势 |

状态四态：`HEALTHY` / `DEGRADED` / `DOWN` / `UNKNOWN`。

**必须依据真实探测结果生成，不能将一次仪表盘请求成功等同于整个系统健康。**

## 4. 统一数据口径

### 4.1 时间维度

统一参数：`startTime`、`endTime`、`comparePeriod`、`granularity`。ISO 8601 或约定业务时区。

### 4.2 交易统计

必须区分三个时间：① 订单创建时间 ② 支付确认时间 ③ 退款成功时间。

**经营现金流口径（默认）**：

| 指标 | 归属时间 |
|---|---|
| 期间成交金额 | 支付确认时间 |
| 期间退款金额 | 退款成功时间 |
| 期间净资金流入 | 两者相减 |

> 退款按实际成功时间归属，**不回溯修改原订单支付期间的现金流**。

**订单批次口径（辅助）**：按支付时间归属订单批次，计算该批次累计退款。

**两种口径不能混为一谈。**

> ✅ **已核实**（CP-DASHBOARD-01 §3）：`orders.paid_time` 与 `payment.paid_time` 在 `PaymentService.onPaid()` 同一事务内写入，可直接用 `orders.paid_time`。现有 `sumPaidAmount` 用的是 `create_time`，必须改造。

### 4.3 订单状态映射

| 业务状态 | 是否纳入成交金额 |
|---|---|
| `PENDING_PAY` | 否 |
| `PAID` | 是，以成功支付记录为准 |
| `COMPLETED` | 是，以成功支付记录为准 |
| `REFUNDING` | 不减少已发生支付金额 |
| `REFUNDED` | 不减少已发生支付金额，退款另行统计 |
| `CANCELLED` / `CLOSED` | 否 |

> ✅ **已核实**：映射与代码一致。另需注意 —— `onPaid()` 确认后立即 `markCompleted`，订单几乎不会停留在 `PAID`，只筛 `PAID` 会返回 0。

**不能仅凭订单状态重复累加支付金额。**

### 4.4 支付统计

待确认收款统计的是**支付单**，不是订单。支付成功金额以业务系统确认的成功支付记录为准。人工转账确认、回调、重复通知与幂等须统一考虑。

### 4.5 内容统计

PV：有效页面浏览事件总数。UV：期间去重访客标识数。

需过滤：后台访问、已识别机器人、无效请求、重复上报。

> ⚠️ **当前 UV 不可用**：代理未透传 UA/IP，访客标识坍缩。修好前 UV 返回 `null` + 原因，不得用 0 或 PV 冒充。

### 4.6 用户统计

| 概念 | 定义 |
|---|---|
| 新用户 | 账户创建时间在期间内 |
| 活跃用户 | 期间内至少一次已定义有效活动的去重用户 |
| 付费用户 | 期间内至少一笔有效成功支付的去重用户 |
| 用户总数 | 当前有效账户数，**标注为快照指标**，不伪装成期间量 |

### 4.7 服务统计

需求、报价、项目、里程碑各用自身状态。**不得把需求数、报价数、项目数简单相加当作客户数或业务量。**

逾期以业务约定截止时间、当前状态与业务时区为准。

## 5. 后端 API 设计

### 5.1 原则

统一前缀 `/admin/dashboard`。现有 `/admin/stats/sales` 与 `/admin/orders` 迁移期继续保留。

旧 `/admin/dashboard` 先核查消费者，再决定保留、迁移或废弃。**不得因路径相似直接覆盖旧接口。**

### 5.2 接口清单

| 接口 | 功能 | 优先级 |
|---|---|---|
| `GET /admin/dashboard/overview` | 经营核心指标 | P0 |
| `GET /admin/dashboard/trends` | 经营趋势 | P0 |
| `GET /admin/dashboard/todos` | 业务待办 | P0 |
| `GET /admin/dashboard/content` | 内容运营 | P1 |
| `GET /admin/dashboard/users` | 用户运营 | P1 |
| `GET /admin/dashboard/products` | 商品运营 | P2 |
| `GET /admin/dashboard/services` | 服务交付 | P2 |
| `GET /admin/dashboard/health` | 平台健康 | P3 |

是否新建 Controller / Service / Mapper 由代码结构审计决定（结论见 `dashboard/03-API-MAPPING.md`）。

### 5.3 统一请求参数

`GET /admin/dashboard/overview?startTime=2026-11-01T00:00:00%2B08:00&endTime=2026-12-01T00:00:00%2B08:00&comparePeriod=true`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `startTime` | datetime | 是 | 统计开始 |
| `endTime` | datetime | 是 | 统计结束 |
| `comparePeriod` | boolean | 否 | 是否对比上一周期 |
| `granularity` | string | 否 | `HOUR` / `DAY` / `WEEK` / `MONTH` |

校验：开始 < 结束、跨度受控、不接受非法日期、统一时区、统一区间边界。

### 5.4 Overview 响应

```json
{
  "code": 200,
  "data": {
    "period": {"startTime": "...", "endTime": "...", "timezone": "Asia/Shanghai"},
    "salesAmount": 0,
    "refundAmount": 0,
    "netAmount": 0,
    "pendingPaymentCount": 0,
    "newOrderCount": 0,
    "paidOrderCount": 0,
    "averageOrderValue": 0,
    "currency": "CNY",
    "comparison": null,
    "updatedAt": "..."
  }
}
```

> 以上为目标契约，不代表现有 DTO 已存在。金额统一 `DECIMAL` / `BigDecimal`，**禁止浮点数做财务计算**。

### 5.5 Trends 响应

统一时间序列：时间桶、成交金额、退款金额、净资金流入、成交订单数。**缺失时间桶补零。**

### 5.6 Todos 响应

每项提供：`type`、`count`、`priority`、`earliestCreatedAt`、`targetRoute`。

**`targetRoute` 必须是后台实际存在的路由，且该页面必须真的消费筛选参数**（审计发现 5 个目标中 4 个不读 query，见 §8 阶段 1 任务）。

### 5.7 其他四域

每个接口只负责对应域统计。排行榜须支持排序方式、返回数量、时间范围、空数据状态。

**详情数据使用已有业务接口，不在仪表盘接口中重复返回完整业务实体。**

### 5.8 Health 响应

返回：`component`、`status`、`checkedAt`、`latencyMs`、`message`、`lastSuccessAt`。

错误信息**不得泄露**数据库凭证、内部 IP、堆栈或密钥。

## 6. 数据来源与数据库设计原则

### 6.1 现有数据优先复用

不能在未检查表结构前确定 Mapper 或 SQL。开发前建立数据映射（已完成，见 `dashboard/02-DATA-MAPPING.md`）。

| 统计域 | 必须核对 |
|---|---|
| 经营 | 订单、订单明细、支付、退款 |
| 内容 | 文章、分类、发布状态 |
| 流量 | `visit_log`、访客标识、访问时间 |
| 用户 | 账户、注册时间、状态 |
| 商品 | 商品、类型、上下架 |
| 服务 | 需求、报价、项目、里程碑 |
| 健康 | Quartz 执行记录、服务探测、应用日志 |

### 6.2 不重复建立业务数据

仪表盘是**只读聚合视图**。不允许：复制订单、建第二套支付记录、建重复的项目状态、用前端计算替代后端财务统计、把访问日志当订单事实。

### 6.3 是否需要汇总表

**首期不新增汇总表。** 先做 EXPLAIN、真实数据量测试与接口性能测试，确认影响性能后再设计。

> **唯一例外**：`blog_view_daily`。它的必要性不是性能，而是 `visit_log.content` 存的是标题字符串、无法作为稳定维度。见 `02-DATA-MAPPING.md` §7.2。

### 6.4 Redis 使用原则

可缓存：经营统计结果、趋势图结果、内容排行榜、用户统计快照。

不建议缓存：待确认收款的最终操作依据、退款处理状态、需立即处理的待办。

所有缓存必须设 TTL 并支持主动失效。

## 7. 前端页面结构

**第一屏**：标题与时间筛选 → 经营核心指标卡 → 成交/退款/净收入趋势 → 业务待办摘要 → 最近订单。

**第二屏**：内容运营 → 热门文章排行 → 用户增长趋势。

**第三屏**：商品运营 → 商品销售排行 → 服务需求与项目交付。

**第四屏**：平台健康度 → 系统异常与任务执行。

**交互**：

- 修改时间筛选后统一刷新关联模块
- 刷新按钮重取当前范围
- 模块独立加载状态，单模块异常不影响其他模块
- 无数据展示空状态
- 所有指标提供口径说明
- 点击统计卡进入对应业务列表，点击排行进入详情

**不得通过一次失败请求将所有模块标记为零。**

- 建立必要的事件关联方案

验收：PV/UV 定义明确且可重复验证；注册/活跃/付费互不混淆；无法实现的渠道归因明确标记"暂不可统计"。

### Phase 3：商品运营与服务交付

- 商品统计、销量排行、成交金额排行、访问与转化
- 服务需求、报价、项目、里程碑逾期统计
- 接入业务详情页

验收：商品金额与订单明细核对一致；服务待办与服务管理页一致；项目与里程碑状态完全遵循现有规则。

### Phase 4：平台健康度

- 接入 Java API 健康检查、MySQL、Redis、文件存储、AI 服务、Quartz、支付回调异常、应用异常

验收：健康状态来自真实探测；探测失败不得显示为正常；**不得将业务接口错误等同于基础设施宕机**。

### Phase 5：AI 经营分析（暂不实施）

前置：核心口径稳定、关键指标可追溯、经营数据经过验证、业务域接口稳定、有足够历史数据。

AI **只能读取授权范围内的统计结果**，不得自行修改订单、退款或业务状态。所有建议须展示对应数据依据。

---

## 9. 测试与质量要求

**单元测试**：时间范围计算、金额计算、订单状态过滤、支付状态过滤、退款时间归属、用户去重、PV/UV 去重、待办状态过滤、趋势桶补零。

**集成测试**：经营总览与订单/支付/退款管理一致、内容与访问日志一致、用户与账户管理一致、商品与订单明细一致、服务与服务管理一致。

**前端测试**：默认/自定义时间范围、切换、刷新、并发请求、单模块失败、全部无数据、图表空状态、页面跳转、权限不足。

**性能目标**：常规统计 P95 ≤ 1 秒；复杂分析 P95 ≤ 2 秒；首屏主要内容 2 秒内呈现；单模块异常不阻塞整页；大范围统计限制跨度。以实测为准。

---

## 10. 权限与安全

沿用现有认证与权限。仪表盘只读当前管理员有权查看的数据。健康检查不暴露敏感配置。经营数据不泄露用户隐私。金额与订单不由前端推算。API 校验时间参数、防止超大范围查询。**不允许前端直连数据库。**

---

## 11. 版本交付标准

首期至少包括：完整经营总览、统一时间筛选、经营趋势、业务待办、最近订单、真实统计口径、自动化测试、接口文档、数据来源映射、页面功能说明、旧接口处理结论。

**所有统计必须能通过 SQL 或业务记录人工复核。**

---

## 12. 最终产品定义

后台仪表盘不再是销售统计页面，而是整个技术平台的统一经营管理入口。

核心能力：

> **看经营、看内容、看用户、看商品、看服务、看待办、看系统。**

演进顺序：数据准确 → 经营可视 → 业务可执行 → 系统可观测 → AI 辅助决策。

**本次重构优先保证现有业务体系的完整性和数据可信度，不以增加图表数量作为项目完成标准。**

## 附录 B：三个强制质量门

### G1 统计数据可追溯

每个指标必须有：指标定义、数据表及字段、SQL 计算规则、状态过滤条件、时间归属规则、验证样例。

**没有完整证据的指标不得标记为已完成。**

### G2 业务数据一致性

仪表盘数据必须与对应业务管理页面核对一致：待确认收款 = 支付管理待确认数；待处理退款 = 退款管理待处理数；进行中项目 = 项目管理对应状态；商品销售额 = 订单明细计算值。

### G3 不能破坏现有业务

不改变订单状态机、支付确认流程、退款审批流程、商品购买与权益发放、服务项目状态机；不擅自删除历史访问数据；不直接删除旧接口。
