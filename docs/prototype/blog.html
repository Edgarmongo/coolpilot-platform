运维实录SSH安全

44,256 次失败登录之后：一次真实的 VPS 加固实录

加固只花了十分钟，但我中途三次把自己锁在门外。完整过程、两个看起来很蠢但很多人会犯的错误，以及 sshd 配置「先读到为准」这条必须知道的规则。

2026-11-19· 12 分钟· 1,842 次阅读· Ubuntu 24.04 / OpenSSH 9.6

先说结论：这台机器在被持续爆破，但没被攻破。真正危险的不是「有人猜中密码」，而是 root 直接暴露在公网、允许密码登录、没有任何自动封禁——这三件事同时成立时，被猜中只是时间问题。

环境：Ubuntu 24.04 LTS / OpenSSH 9.6p1 / 已连续运行 53 天。以下所有数字与日志都来自这台机器，不是示例数据。

一、先量一下风险，而不是先改配置

动手之前先做了三件事：看生效配置、看历史爆破量、看当前有没有兜底通道。

sshd -T | grep -iE "^(permitrootlogin|passwordauthentication|maxauthtries)"
# permitrootlogin yes
# passwordauthentication yes
# maxauthtries 6

grep -c "Failed password" /var/log/auth.log
# 44256

四万四千次失败登录，来源高度集中——前五名里有四个属于同一网段，典型的僵尸网络轮换 IP。这说明它不是针对你，而是无差别扫描；但只要密码够弱，无差别扫描一样能进来。

二、方案：四步，顺序不能错

步骤做什么顺序要求
1装公钥并验证能登录必须在关密码前
2关掉密码认证确认第 1 步成功
3装 fail2ban先设白名单
4启用防火墙先放行 22

第 1 步做完之前绝不能动第 2 步。我见过最惨的情况是顺序反了：密码关了、公钥没生效，直接从 SSH 里被踢出去。

三、我把自己锁在门外三次

第一次：systemctl enable --now fail2ban 在服务已经被 apt 拉起的情况下是空操作，我写的 jail.local 从未被加载，白名单一直是空的，于是我的出口 IP 被自己的规则封了。

第二次：把「装 fail2ban」和「启 ufw」放在同一条命令里。两个都会影响登录的变更叠加在一起，出问题时分不清是哪个。

第三次：用 VNC 修配置时，多行内容一行行粘贴会错乱，导致文件写坏。

后来改成了一个规矩：一条命令只改一个可能影响登录的变量，改完立刻用新连接验证，通过再做下一个。

四、真正容易踩的坑：sshd 先读到为准

我把加固配置写成 99-hardening.conf，重启后 passwordauthentication 仍然是 yes。原因不在语法，而在加载顺序：

# /etc/ssh/sshd_config.d/
50-cloud-init.conf    → PasswordAuthentication yes
99-ctrl.conf          → PasswordAuthentication yes
99-hardening.conf     → PasswordAuthentication no   ← 被忽略

sshd 对同一指令取第一次读到的值，不是最后一次。所以文件名必须排在这两个文件前面，改成 00-hardening.conf 才生效。

五、最终状态

项之前现在
root 密码登录开启关闭
密码认证开启关闭
认证尝试上限6 次3 次
爆破防护无fail2ban（10 分钟 5 次封 1 小时）
防火墙未启用放行 22 / 80 / 443

验证方式很土但有效：新开一个连接，密钥能进，密码被拒。

ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no root@host
# Permission denied (publickey).   ← 这就是想要的结果
没验证的部分：本文只覆盖单机场景，未涉及跳板机、多用户 sudo 模型、以及密钥轮换流程。这些会单独写。
