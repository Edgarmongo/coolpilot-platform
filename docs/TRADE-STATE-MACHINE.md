## 一、订单状态

```
                    ┌──────────────┐
     下单            │ PENDING_PAY  │  待支付（30 分钟有效）
   ────────────────► │              │
                    └──┬────┬───┬───┘
        提交转账凭证     │    │   │  30 分钟未付 / 定时任务
      ┌───────────────┘    │   └──────────────┐
      ▼                    │                  ▼
┌──────────────────┐  用户取消          ┌──────────┐
│ PENDING_CONFIRM  │ ─────────────►    │ CLOSED   │
│ 待确认收款        │  （仅 PENDING_PAY  │ 已关闭    │
└────────┬─────────┘    可取消）        └──────────┘
         │ 后台确认到账
         ▼
   ┌──────────┐   申请退款    ┌───────────┐  退款完成  ┌──────────┐
   │   PAID   │ ───────────► │ REFUNDING │ ────────► │ REFUNDED │
   │  已支付   │              │  退款中    │           │ 已退款    │
   └────┬─────┘              └───────────┘           └──────────┘
        │ 交付完成
        ▼
   ┌──────────┐
   │COMPLETED │
   │ 已完成    │
   └──────────┘
```

| 状态 | 中文 | 谁推进它 |
|---|---|---|
| `PENDING_PAY` | 待支付 | 用户下单 |
| `PENDING_CONFIRM` | 待确认收款 | 用户提交转账凭证 |
| `PAID` | 已支付 | 后台确认到账 |
| `COMPLETED` | 已完成 | 交付完成 |
| `CANCELLED` | 已取消 | 用户（仅待支付） |
| `CLOSED` | 已关闭 | 超时 / 定时任务 |
| `REFUNDING` | 退款中 | 用户申请 |
| `REFUNDED` | 已退款 | 后台同意退款 |

## 二、支付单状态

订单和支付单是**一对多**：一个订单可以有多笔支付尝试（换渠道、失败重来）。

| 状态 | 含义 | 如何离开 |
|---|---|---|
| `INIT` | 已创建，未付款 | 用户取消订单时关闭；或超时 |
| `WAIT_CONFIRM` | 用户已提交转账凭证，等后台确认 | 后台确认 → `SUCCESS`；或关闭 |
| `SUCCESS` | 收款成功 | 终态 |
| `CLOSED` | 已关闭 | 终态 |

**关键关联**：`onPaid()` 里先标记支付单成功，再 `orderMapper.markPaid(orderNo)`。
后者是带状态条件的 UPDATE —— 影响行数为 0 说明订单已经被别人推进过（比如重复确认），
此时抛「订单状态已变化」。这是**幂等的最后一道闸**。

---

## 三、权益（entitlement）

支付确认后按订单明细发权益，`entitlement` 记录 `user_id + product_id` 的唯一持有关系。

- 发放时机：`PaymentService.onPaid()` 成功后
- 幂等依据：`entitlementMapper.countActive(userId, productId)`，已持有则不再发
- 下单前置检查：已持有权益时拒绝下单（"你已拥有该商品，可直接查看"）

**改这块的红线**：发放逻辑必须与 `markPaid` 在**同一个事务**里，
否则会出现「钱收了、权益没发」或「权益发了、订单还是待支付」。

---

## 四、并发保护（三层，都要保住）

| 层 | 机制 | 在哪 |
|---|---|---|
| 1 | Redis `setIfAbsent` 10 秒 | `OrderService.guardRepeatedSubmit` 防连点 |
| 2 | 复用未支付订单 | `orderMapper.findPending` 避免重复建单 |
| 3 | 带原状态条件的 UPDATE | `markPaid` / `cancel` / `close`，谁抢到算谁的 |

**第 3 层是根本**：前两层只是减少冲突，真正保证一致性的是条件 UPDATE + 检查影响行数。
重写时**绝不能**改成"先查状态再更新"——那是典型的竞态漏洞。

---

## 五、金额规则

- 只按商品当前售价计算，**前端传的金额一律不看**
- `FIXED` 价格模式才能直接下单；`STARTING` / `CUSTOM` 必须走人工报价
- 免费商品拒绝下单
- 订单存 `total_amount` / `discount_amount` / `pay_amount` 三个值，明细存单价快照

---

## 六、重写时的检查清单

改 `modules/trade` 任何一个服务，以下每条都要过：

- [ ] 状态流转仍是「带原状态条件的 UPDATE」，不是「先查后改」
- [ ] 影响行数为 0 时仍抛「订单状态已变化，请刷新后重试」
- [ ] `onPaid` 的顺序仍是：支付单 → 订单 → 权益，且在同一事务
- [ ] 权益发放仍按 `countActive` 幂等
- [ ] 金额仍只取商品表的 `price`，不读请求参数
- [ ] 防连点 key 格式不变（`order:submit:{userId}:{productId}`）
- [ ] 下单仍复用未支付订单

**回归方式**：本地起服务，用真实接口走一遍
「下单 → 提交凭证 → 后台确认 → 查权益」，
再走一遍「下单 → 取消」，最后确认 `orders` / `payment` / `entitlement` 三张表的数据一致。
